# DUCAT conformance vectors

Language-neutral test vectors for the DUCAT wire format and contract logic
(protocol §18.9). A client claims conformance against a named vector-set
release.

    vectors/v1/
      manifest.json    metadata, counts, and an explicit statement of what is NOT covered
      codec.json       deterministic CBOR (§18.1) and integer-piconero money (§18.2)
      signing.json     domain separation, cross-context replay, key encoding (§18.3)
      state.json       transitions, deadlines, and refusals (§18.4, §6.2)
      negotiate.json   suite/version selection and the downgrade attempt (§18.6)

## How to read a case

Every case carries a `why` explaining what it defends against — these are not
arbitrary inputs, and an implementer who understands the reason will find the
bug faster than one who only sees a failing hex string.

```json
{
  "name": "overlong_uint_23",
  "why": "a longer-than-necessary integer encoding is not canonical",
  "input_hex": "1817",
  "expect": { "ok": false, "reject_code": 10, "reject_name": "Malformed" },
  "hint": "23 is the last immediate-form value"
}
```

`reject_code` is a **§18.5 wire code**. Two clients must agree that an input is
`MALFORMED`; they need not agree on which internal rule said so. `hint` is
non-normative and names the specific rule, to save you bisecting your decoder.

## The case that matters most

`piconero_2pow53_plus_1` encodes 9007199254740993 — the first integer an IEEE
double cannot represent. It exists specifically so that a client which routes
amounts through a float fails here rather than in production, silently, on
somebody's fare.

## Determinism

All keys derive from fixed seeds and nothing consults a clock or an RNG.
Regenerating on an unchanged implementation produces byte-identical files, so
`git diff` shows real changes only:

    cd core && cargo run --example gen_vectors

## Honest status

These vectors were generated by, and are currently validated only by, the
reference implementation in `core/`. **That means they encode this
implementation's bugs as though they were the specification.** They close
open problem O18 when a second, independent client runs them and disagrees —
not before.

`manifest.json` lists what is not yet covered. The largest gap is §18.9(4),
full per-profile transcripts, which is blocked on the spec fixing field
numbering for `TapPresent`, `FullOffer`, and `ACCEPT`. Until those exist there
is no wire object to build a transcript from.
